# Tasks: Module 4: Vision-Language-Action (VLA)

**Input**: Design documents from `/specs/005-vla/`
**Prerequisites**: plan.md (required), spec.md (required for user stories)

**Tests**: The feature specification for Module 4 includes functional tests and does not explicitly request a TDD approach for every component. Therefore, test tasks will focus on integration and end-to-end validation.

**Organization**: Tasks are grouped by user story to enable independent implementation and testing of each story.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: Which user story this task belongs to (e.g., US1, US2, US3)
- Include exact file paths in descriptions

## Path Conventions

- **Single project**: `src/`, `tests/` at repository root
- Paths shown below assume single project, as defined in `specs/005-vla/plan.md`

## Phase 3: User Story 1 - Voice Command to Text Conversion (Priority: P1) 🎯 MVP

**Goal**: Students will be able to convert spoken voice commands into text using Whisper, forming the initial step of the Vision-Language-Action pipeline.

**Independent Test**: Can be fully tested by running a voice command through Whisper and verifying that the correct textual transcription is produced.

### Implementation for User Story 1

- [ ] T007 [P] [US1] Create basic Whisper interface script in `src/whisper_interface/whisper_node.py`
- [ ] T008 [US1] Implement voice command recording and processing logic in `src/whisper_interface/whisper_node.py`
- [ ] T009 [US1] Integrate Whisper model for voice-to-text conversion in `src/whisper_interface/whisper_node.py`
- [ ] T010 [US1] Publish transcribed text to a ROS 2 topic (e.g., `/vla/voice_command_text`) in `src/whisper_interface/whisper_node.py`
- [ ] T011 [US1] Create a simple test script to validate Whisper transcription accuracy in `tests/whisper_interface/test_whisper_accuracy.py`

**Checkpoint**: At this point, User Story 1 should be fully functional and testable independently

## Phase 4: User Story 2 - LLM-based Cognitive Planning (Priority: P1)

**Goal**: Students will learn to use Large Language Models (LLMs) for high-level task planning, translating natural language commands into a sequence of executable robot actions.

**Independent Test**: Can be fully tested by providing a natural language command to an LLM and verifying that it generates a logical and correct sequence of robot actions or sub-goals.

### Implementation for User Story 2

- [ ] T012 [P] [US2] Create LLM planner script in `src/llm_planner/llm_task_planner.py`
- [ ] T013 [US2] Implement intent extraction from natural language commands using LLMs in `src/llm_planner/llm_task_planner.py`
- [ ] T014 [US2] Implement task breakdown logic using LLMs to generate action sequences/graphs in `src/llm_planner/llm_task_planner.py`
- [ ] T015 [US2] Subscribe to `/vla/voice_command_text` and publish LLM-generated plans to a ROS 2 topic (e.g., `/vla/high_level_plan`) in `src/llm_planner/llm_task_planner.py`
- [ ] T016 [US2] Create a test script to validate LLM planning logic (e.g., for "Clean the room" and "Pick up the cup" commands) in `tests/llm_planner/test_llm_planning.py`

**Checkpoint**: At this point, User Stories 1 AND 2 should both work independently

## Phase 5: User Story 3 - Natural Language to ROS 2 Action Conversion (Priority: P2)

**Goal**: Students will be able to convert the high-level plans generated by LLMs into concrete ROS 2 actions that a robot can execute.

**Independent Test**: Can be fully tested by taking an LLM-generated action sequence and successfully converting it into executable ROS 2 action server calls or messages, verifying proper command formatting and target execution.

### Implementation for User Story 3

- [ ] T017 [P] [US3] Create ROS 2 action server/client setup in `src/ros2_vla_actions/robot_action_server.py` and `src/ros2_vla_actions/robot_action_client.py`
- [ ] T018 [US3] Implement logic to convert LLM-generated plans into ROS 2 action goals in `src/ros2_vla_actions/robot_action_client.py`
- [ ] T019 [US3] Subscribe to `/vla/high_level_plan` and send ROS 2 action goals to the robot in `src/ros2_vla_actions/robot_action_client.py`
- [ ] T020 [US3] Simulate robot execution of ROS 2 actions (e.g., print action received, mock movement) in `src/ros2_vla_actions/robot_action_server.py`
- [ ] T021 [US3] Create a test script to validate ROS 2 action conversion and basic execution flow in `tests/ros2_vla_actions/test_action_conversion.py`

**Checkpoint**: All user stories should now be independently functional

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies - can start immediately
- **Foundational (Phase 2)**: Depends on Setup completion - BLOCKS all user stories
- **User Stories (Phase 3+)**: All depend on Foundational phase completion
  - User Story 1 (P1) and User Story 2 (P1) can proceed in parallel (if staffed)
  - User Story 3 (P2) depends on User Story 2 for high-level plans.
- **Polish (Final Phase)**: Depends on all desired user stories being complete

### User Story Dependencies

- **User Story 1 (P1)**: Can start after Foundational (Phase 2) - No dependencies on other stories
- **User Story 2 (P1)**: Can start after Foundational (Phase 2) - No dependencies on User Story 1, but processes output from US1.
- **User Story 3 (P2)**: Can start after Foundational (Phase 2) - Depends on User Story 2 for high-level plans.

### Within Each User Story

- Tasks within a story follow a logical progression (e.g., scripts before integration, core logic before publishing).
- Tests (if included) should ideally be written before implementation, but for this module, they are focused on validation after core logic.

### Parallel Opportunities

- All Setup tasks marked [P] can run in parallel.
- Tasks within User Story 1 (P1) can have some parallel aspects (e.g., creating scripts).
- Tasks within User Story 2 (P1) can have some parallel aspects.
- User Story 1 and User Story 2 can be worked on in parallel by different team members.
- Tasks within User Story 3 (P2) can have some parallel aspects.
- Tasks within the Polish phase marked [P] can run in parallel.

## Implementation Strategy

### MVP First (User Story 1 Only)

1. Complete Phase 1: Setup
2. Complete Phase 2: Foundational (CRITICAL - blocks all stories)
3. Complete Phase 3: User Story 1
4. **STOP and VALIDATE**: Test User Story 1 independently
5. Deploy/demo if ready

### Incremental Delivery

1. Complete Setup + Foundational → Foundation ready
2. Add User Story 1 → Test independently → Deploy/Demo (MVP!)
3. Add User Story 2 → Test independently → Deploy/Demo
4. Add User Story 3 → Test independently → Deploy/Demo
5. Each story adds value without breaking previous stories

### Parallel Team Strategy

With multiple developers:

1. Team completes Setup + Foundational together
2. Once Foundational is done:
   - Developer A: User Story 1
   - Developer B: User Story 2
   - Developer C: User Story 3 (dependent on US2, so B needs to finish core US2 first)
3. Stories complete and integrate independently
